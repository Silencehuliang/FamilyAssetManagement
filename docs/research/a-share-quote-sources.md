> 检索日期：2026-09-15 ｜ 调研人：研究助理（CodeBuddy）
> 目的：为部署在 Cloudflare 免费套餐（Workers/Pages Functions，每请求 CPU 上限 10ms）的「每日收盘抓取 A 股行情」定时任务，选定稳定、零成本、可长期运行的数据源。

## 2. 各源实际情况（含实测返回片段）

### 2.1 新浪实时 `hq.sinajs.cn` ✅实测
- **请求**：`https://hq.sinajs.cn/list=sh601006,sz000001`（批量用逗号）。
- **实测返回**（2026-09-15 13:46，已脱敏格式）：
  ```
  var hq_str_sh601006="大秦铁路,4.820,4.810,4.780,4.840,4.770,4.770,4.780,91237413,438525521.000,...,2026-09-15,13:46:00,00";
  ```
- **字段口径（逗号分隔，下标从 0）**：0=名称，1=今开，**2=昨收**，**3=最新价(当前价)**，4=最高，5=最低，6=买一，7=卖一，8=成交量(股)，9=成交额(元)，10~29=五档买卖盘，**30=日期(YYYY-MM-DD)**，**31=时间(HH:MM:SS)**，32=状态码（实测为 `00`，疑似正常；枚举未权威文档化）。

- **编码**：返回 **GBK/GB2312**；不解码中文会乱码（📄 文档一致；实测抓取到中文正常，环境已解码）。

## 3. Cloudflare Workers 抓取这些源的可行性（架构关键点）

- **明文 HTTP 子请求是否被允许？** 查 Cloudflare 官方文档：
  - Compatibility Flags 文档明确 `fetch()` 接受 `http:` 与 `https:` 协议（原文：「any protocol other than http: or https: ... would silently treat it as http:」），即 **http: 是一等支持的协议**。
  - Node.js `http` 兼容文档中**实际示例** `get('http://docs.cloudflare.com/...')` 收到 `301`（重定向到 https），证明 **Workers 确实能对外发起明文 HTTP 子请求**。
  - 结论：**即便某源只有 HTTP，Workers 也能 fetch**；浏览器侧的「混合内容拦截」不适用 Workers。
- **但本系统无需依赖 HTTP**：如上，四个候选**实测均支持 HTTPS**，直接全部走 HTTPS，规避任何明文相关不确定性。
- **免费套餐约束（官方文档）**：
  - 每日请求上限 **100,000**；突发 **1,000 次/分钟**；每请求子请求上限 **50**；每请求 **CPU 10ms**（网络 I/O 不计入 CPU，仅计计算）；**Cron Triggers 免费套餐可用**。
  - 本场景：2 用户、每日 1 次抓取（几只持仓股）→ 请求量与子请求数均远低于上限，**10ms CPU 也足够**（仅做字符串拆分）。
- **GBK 解码注意（建议）**：新浪/腾讯返回 **GBK**，Workers `TextDecoder` 对 `gbk/gb2312` 的支持取决于兼容性日期，需上线前确认；**最稳做法是用东方财富（UTF-8 JSON）做主/备以规避 GBK**。

## 4. 交易日历 / 停牌 / 非交易时段

> 以下除标注 ✅ 外均为 📄 第三方经验或推导，因当前为交易时段无法实测盘前/盘后/停牌。

- **交易日历**：这些免费接口**都不提供可靠的交易日历**。建议单独维护一份交易日列表，来源可选：
  - 上交所/深交所官网发布的年度休市安排（最权威）；
  - 或 AKShare `tool_trade_date_hist_sina` 等现成日历（📄 社区）。
  - 定时任务应**只在交易日触发**（Cron 每周一至五 + 代码内交易日判断）。
- **停牌判断（无干净布尔字段）**：新浪/腾讯基础 feed 没有明确的 `suspend` 布尔。稳健启发式（📄 SegmentFault 多方经验）：
  - **成交量 == 0**（新浪字段 8 / 腾讯字段 6）且价格长时间冻结 + 时间戳（新浪字段 31 / 腾讯字段 30）不再推进 → 疑似停牌；
  - 东方财富实时 `f168` 疑似状态位（实测=8，**枚举未文档化**，需自行标定）。
  - 优先用「状态字段 + 时间戳心跳 + 横向对比同批其他票」三层判定，避免把网络中断/非交易时段误判为停牌。
- **非交易时段「最新价」取值**：📄 社区文档称盘后/休市时新浪返回当前价=0 或=昨收、成交量为 0；腾讯部分盘口字段留空。**本系统的最佳实践**：把每日抓取 Cron 排在**收盘后（如北京时间 15:30）**，此时「最新价」即当日收盘价；并加一道校验——返回里的日期字段（新浪 30 / 腾讯 30）必须等于「今天」，否则视为陈旧数据、走降级。

## 5. 合规说明

- **接口性质**：新浪 `hq.sinajs.cn`、腾讯 `qt.gtimg.cn`、东方财富 `push2*/push2his*` 均为**非公开的内部接口**，无面向第三方的官方 API 文档与服务条款（ToS），**无 SLA、无稳定性承诺**。新浪 2022 年加 Referer 即为「随时可改」的先例。
- **个人自用 vs 公开托管**：
  - **家庭自用、2 人、每日 1 次低频** → 属个人非商业、低频率使用，风险低；建议**不要对外公开暴露这些抓取端点**，也不要把抓来的数据再分发/商业化。
  - **公开托管给他人访问 / 高频 / 商业** → 触发反爬封禁与 ToS 争议的风险显著上升，且可能因「抓取未授权数据」引发合规问题。
- **数据用途**：仅用于个人记账与收益估算，**不构成投资建议**；历史/实时数据以交易所官方为准。
- **稳健做法**：低频 + 本地缓存 + 多源降级 + 手动兜底；不依赖单一源；监控连续失败并告警。

## 6. 结论与推荐

### 6.1 排序推荐
| 用途 | 首选 | 备选 |
|------|------|------|
| 每日收盘快照（最新价/昨收/今开） | **腾讯 `qt.gtimg.cn`**（✅ 实测，无需 Referer，字段多年稳定，UTF-8 友好） | **新浪 `hq.sinajs.cn`**（✅ 实测，用户偏好「新浪等稳定」，需带 Referer，GBK） |
| 历史日线回填 | **东方财富 `push2his.eastmoney.com`**（✅ 实测，UTF-8 JSON，字段清晰） | **新浪 `money.finance.sina.com.cn`**（✅ 实测，UTF-8 JSON） |

> 说明：用户点名「新浪等稳定可靠的」。新浪实测确实可用，但腾讯在「无需 Referer、字段稳定、UTF-8」上更省心，故**主源建议腾讯、备源新浪**；若坚持以新浪为主亦可，只要在生产代码里固定带 Referer 并做 GBK 解码与降级。历史日线首选东方财富（JSON 最易解析、最稳）。

### 6.2 降级链路（每日收益计算）
```
每日 15:30（仅交易日）Cron 触发
  └─ 调主源（腾讯 qt.gtimg.cn）
       ├─ 成功且日期==今天且成交量合理 → 写入「当日市值/最新价」
       └─ 失败/超时/数据陈旧
            └─ 调备源（新浪 hq.sinajs.cn，带 Referer，GBK 解码）
                 ├─ 成功 → 写入
                 └─ 仍失败
                      └─ 调历史日线源确认（东方财富 push2his）补全
                           └─ 全部失败 → 标记「当日市值待录入」，
                                允许成员手动录入当日市值（系统已有「未交易金额」录入通道）
```
- 历史回填一次性跑：东方财富 `push2his` 批量按代码逐只拉日线 → 落库；缺段用新浪历史接口补齐；两者皆失败则留空、人工补。
- 监控：连续 N 日主备全失败 → 通知成员手动录入，避免收益计算中断。

### 6.3 关键风险清单
1. 非官方接口，可能随时改版/加鉴权（新浪已有先例）→ **必须多源 + 手动兜底**。
2. 新浪需 Referer 且 GBK 解码 → 生产务必处理；否则优先用腾讯/东财（UTF-8）。
3. 免费套餐无 SLA、限流靠社区经验 → 低频使用、加缓存、加监控。
4. 停牌/非交易时段无干净字段 → 用「成交量+时间戳+日期校验」判定，并在收盘后抓取。
5. 交易日历需自备（交易所官网或 AKShare 日历），不可依赖行情接口。

## 7. 补充实测：历史日线的复权口径与回填成本（2026-09-15，为 «持仓快照与历史收益表设计» 复核）

> 本节补全 §2.4 未记录的 `fqt` 语义与 `data.dktotal`，**并修正一处调研层面的前提**。
> 取证通道：本节四项均为 `push2his` 直连实测（本机 curl 被环境网络拦截，改经工具通道，字段与数值与 §2.4 同源）。

### 7.1 一次请求返回全部历史 ⇒ 回填成本与「深度」无关 ✅**实测**

`beg` / `end` 只是参数：`beg=0&end=20500101` 一次返回 `data.dktotal = 6005` 根日线（≈ 24.6 年）。

**⇒ 回填 N 只股票的成本只与「只数」成正比，与「回填多少天」无关。**
原 §2.4 只注明「单只；多只需多次」，未说明深度不构成成本维度——若按「N 只 × M 天」估算会高估两个数量级（20 只 × 250 天会算成 5,000 请求，实为 20 请求）。

### 7.2 `fqt` 两种口径的实测差异 ✅**实测**

样本 sh600519，除权除息日 **2026-06-26**（10 派 280.2423 元含税 ⇒ 每股 28.02423 元）：

| 日期 | fqt=0（不复权）收盘 | fqt=1（前复权）收盘 |
|---|---|---|
| 2026-06-24 | 1207.68 | 1179.66 |
| 2026-06-25 | 1212.10 | 1184.08 |
| 2026-06-26 | 1168.63 | 1168.63 |

- **fqt=1 的「前一交易日收盘」= 交易所公布的除权（息）参考价**：`1212.10 − 28.02 = 1184.08`，与 fqt=1 在 06-25 的值**逐分吻合**。
  这也正是当日实时 feed 返回的「昨收」——两条独立通道互相印证。
- **fqt=1 的逐日差额 = 真实的当日涨跌**（06-25 → 06-26 为 **−15.45** 元），故可用于「反推昨收」；
  但**不能作为存储口径**（见 7.3）。

### 7.3 前复权序列锚定在「拉取当日」，不是请求窗口 ✅**实测**

同一历史日期、不同请求窗口下，fqt=1 的值**完全相同**；但 `data.preKPrice`（窗口首根的**前一日收盘**）**随 `fqt` 切换**：

| 请求窗口 | fqt=0 preKPrice | fqt=1 preKPrice | 差 |
|---|---|---|---|
| 20260601–20260624 | 1326.00 | 1297.98 | 28.02 |
| 20260618–20260702 | 1240.00 | 1211.98 | 28.02 |

`preKPrice` 的两种口径相差的 28.02 元，正是**当前累计分红**。

**⇒ 推论（重要）：前复权价不能逐日抓取后冻结入库** —— 每条行会各自冻结在**它被抓取那一天**的基准上；一旦期间发生分红，表内相邻两行之间会凭空多出一次分红额的亏损。实测数据可复现：06-24/06-25 在分红前抓取（存 1207.68 / 1212.10），06-26 在分红后抓取（存 1168.63）⇒ 表内 06-25→06-26 为 **−43.47**，而真实为 **−15.45**。

**未实测、待复核**：推测 `preKPrice` 支持「单日窗口」（`beg=end=D` 时返回 D 的前一日收盘），若成立则可作为回填昨收的兜底手段。**上线前须复核。**
