【二】为什么必须「加列 + 索引 + 触发器」三步，而不是一条 DDL
==============================================================================
  [PASS] A1  ALTER TABLE entry ADD COLUMN x TEXT UNIQUE —— 预期被拒
  [PASS] A2  ALTER TABLE entry ADD COLUMN x TEXT NOT NULL —— 预期被拒（无非空默认值）
  -> SQLite 的 ADD COLUMN 既不能加 UNIQUE、也不能加无默认值的 NOT NULL 列，
     故「client_ref 唯一且新行必填」无法靠一次加列实现。这是三步结构的硬依据。

  A3/A4 在一张**独立的临时表**上演示（不在主库里留试验列）：
    [PASS] A3  ADD COLUMN 带 CHECK —— 成功；既有行的 w 未被求值，值为 None
    [PASS] A4  把既有行的 w 改成不合规值 —— 预期被 CHECK 拒
    -> 结论：ADD COLUMN 时不对既有行求值，但**既有行之后一旦被 UPDATE 就会重新求值**。
       0001 的 entry 表上已有 biz_date 的 CHECK，任何 UPDATE 都会重跑它 ——
       故本迁移选择「触发器只管新写入」，语义边界比列上 CHECK 清晰可控。

【五】`INSERT OR IGNORE` 与触发器 `RAISE(ABORT)` 的交互（决定重放 SQL 的形态）
==============================================================================
  [PASS] D1  用 INSERT OR IGNORE 插入 5 个对象 —— 观察 ABORT 是否被吞掉
      实际落库的对象行数 = 0
      -> 结论（本机 3.53.1 实测）：`OR IGNORE` **不会**吞掉触发器里的 `RAISE(ABORT)` ——
         ABORT 照常抛出，语句整体回滚，0 行都没进去。
         即便如此，契约仍**不采用** OR IGNORE，理由有两条：
           ① OR IGNORE 会吞掉**约束类**失败（主键/NOT NULL/CHECK），那正是「写入静默
              不一致」的来源 —— 错误应显式暴露，而不是挑一半吞一半；
           ② `AND NOT EXISTS (...)` 表达的是「这条还没插过」这个**意图**，语义比
              「冲突就忽略」精确，且不依赖冲突解决算法的细节。

【六】整批重放：为什么必须「先预校验、再写 batch」
==============================================================================
  场景：离线队列 3 条，其中第 2 条引用的类别标签已被删除（离线期间别人删的）。

  E1  不做预校验，整批塞进一个事务  ->  error:IntegrityError，净增 0 行
      -> 一条坏数据把整批拖下水。这就是**必须预校验**的实测依据。

  E2  预校验（1 条 SQL）：有效 2 条 / 无效 1 条  ->  无效者：77777777
  E3  只把有效的 2 条放进事务  ->  ok，净增 2 行
  [PASS] E4  逐条结果：3 条中 2 条成功、1 条失败（失败被隔离，不阻塞其余）  ->  2
      -> 一个请求：1 次预校验查询 + 1 个事务。失败的条目原样返回，不进事务。
         ⚠️ 预校验与写入之间理论上存在竞态窗口（这中间标签被删）。2 人自用可忽略，
            且此时事务会整体回滚、不会写入半条 —— 失败是显式的，不是静默的。

【七】重放语句的数据访问路径（三条判据，附一处 EXPLAIN 误用的更正）
==============================================================================

  ⚠️ 先如实登记一处**本票自查踩到的误用**：
     `EXPLAIN QUERY PLAN <INSERT>` **不能用来判断 INSERT 的数据访问路径** ——
     它报告的是该表身上的**外键动作程序**。本机 SQLite 3.53.1 的对照实测：

       INSERT INTO member              -> 6 行，全是「引用 member 的那些子表」的索引查找
       INSERT INTO entry               -> 1 行：SEARCH entry_object（唯一引用 entry 的表）
       INSERT INTO entry_object        -> 0 行（没有任何表引用它）
       INSERT INTO budget_alert_state  -> 0 行（同上）

     三者与「本语句查了哪些表」完全无关。探针最初版本正是在这里误用了它，
     把外键程序当成了全扫证据 —— 那会让「不得全扫」这条判据变成空的。已更正。

  判据一（最硬的一条）：ON CONFLICT 的冲突检测**必然**走唯一索引。
    [PASS] 删掉 ux_entry_client_ref 后，同一语句无法编译：
          error: ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint
    已重建索引。-> ON CONFLICT(client_ref) 这个语义**本身就依赖该唯一索引**；
       索引不存在它就编译不过 ⇒ 不存在「全表扫描找冲突」这条路径。

  判据二：重放涉及的定点查询全部走索引（EXPLAIN QUERY PLAN 用在 SELECT 上是可靠的）
    按 client_ref 取回 id     : SEARCH entry USING COVERING INDEX ux_entry_client_ref (client_ref=?)
    按 client_ref 判重        : SEARCH entry USING COVERING INDEX ux_entry_client_ref (client_ref=?)
    重放对象行定位 entry          : SEARCH e USING COVERING INDEX ux_entry_client_ref (client_ref=?)
    重放对象行定位 entry          : CORRELATED SCALAR SUBQUERY 1
    重放对象行定位 entry          : SEARCH eo USING COVERING INDEX sqlite_autoindex_entry_object_1 (entry_id=?)
    重放对象行定位 entry          : SCAN j VIRTUAL TABLE INDEX 1:
    （`SCAN j VIRTUAL TABLE INDEX` 是 json_each 展开 JSON 数组，属正常，不是表扫描。）

  判据三：新增的唯一索引确实在写入路径上被维护（看 EXPLAIN 字节码）
    字节码中 OP_IdxInsert 出现 4 次；entry 表上共有 4 个索引（ix_entry_cat_date, ix_entry_member_date, ix_entry_biz_date, ux_entry_client_ref），逐个维护。
