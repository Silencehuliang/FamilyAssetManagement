[4] 单日窗口 preKPrice —— 非交易日退化为 0.0，且 0.0 会伪装成合法值
==============================================================================

  请求窗口 beg=end=    是否交易日      preKPrice klines
  20260629             是                1168.63 klines 有 1 根，preKPrice = 前一交易日收盘
  20260628             否                   0.00 klines 为空数组，preKPrice 退化为 0.0

  交易日窗口返回的是**前一交易日**的收盘（按请求的 fqt 口径），可作昨收的一种取得方式；
  但非交易日窗口返回 0.0 —— 我们**没有交易日历**（#8 R10），无法预先知道该挑哪一天，
  因此单日窗口这条路不可用。

  更危险的是这个 0.0：它**结构合法、类型正确**，会穿过所有「非空 / 可解析」的校验。
  若把它当价格入库：当日盈亏 = (152.71 − 0.00) × 数量 ⇒ 一只正常股票凭空 −100%。
  ⇒ 这与已在别处设防的「最新价 == 0 判为解析失败」是**同一条判据**，
    必须同样应用到 prev_close：**prev_close <= 0 一律判为无效、按缺失处理**。

  附：preKPrice 随 fqt 口径切换（差额 = 当前累计分红），故它不是独立字段：
  请求窗口                      fqt=0        fqt=1 差
  20260601-20260624           1326.00      1297.98 28.02
  20260618-20260702           1240.00      1211.98 28.02

[5] 东财分红接口 RPT_SHAREBONUS_DET 的解析陷阱与可用过滤形态
==============================================================================

  过滤形态（均为 2026-09-15 实测可用）：
    ① 单码全历史   filter=(SECURITY_CODE="600519")                → 返回 28 条（回溯至 2002 年）
    ② 多码 in       filter=(SECURITY_CODE in ("600519","000001")) → 返回两码混合清单
    ③ 日期区间      filter=(EX_DIVIDEND_DATE>='2026-09-15')(..<='2026-09-15')
                    → 返回全市场当日除权名单（当日共 14 条）⇒ **N 只股票只需 1 个请求**

  陷阱：返回中含 **EX_DIVIDEND_DATE 为 null 的记录** —— 茅台全历史 28 条中有 1 条是
        分红预案（如「分红金额上限不超过公司2026年上半年实现归属于上市公司股东的净利润」），
        其 ex-date 与派息金额均为 null。
  若不过滤：
    ① 会生成一条**没有日期的「除权建议」**，前端无法渲染、成员无法处理；
    ② 会破坏 corporate_action 的 `(member_id, code, ex_date)` 唯一键（NULL 在 SQLite 中
       不参与唯一性比较 ⇒ 每次抓取都会插入一条新行，**建议无限增殖**）。

  实测：同一批记录（5 条有效 + 1 条预案）跑 **2 次**后的行数对比：
    建表方式                                       行数 结论
    ① 裸表，无唯一约束                               12 每条各插一次 ⇒ 全面增殖
    ② 唯一约束，但不过滤 null                         7 5 条有效被去重，**NULL 那条第 2 次仍插入** ⇒ 仍增殖
    ③ 过滤 null + (成员,代码,除权日) 唯一             5 幂等 ✓
    变体 ② 中 ex_date 为 NULL 的行数 = 2/2 —— **唯一约束对 NULL 完全无效**
    ⇒ 结论：**「过滤 null」与「唯一约束」缺一不可**，光有唯一键挡不住预案记录。

  字段形态（实测）：PRETAX_BONUS_RMB 是**每 10 股含税派息**（元），
  BONUS_IT_RATIO / BONUS_RATIO / IT_RATIO **实测为 null**，送转比例只能从
  IMPL_PLAN_PROFILE 文本解析（「10送1.00派43.74元」「10转10.00派3.00元」）：
    除权日          每10股派息 方案原文
    2026-06-26        280.2423 10派280.2423元(含税)
    2025-12-19          239.57 10派239.57元(含税,扣税后215.613元)
    2025-06-26          276.73 10派276.73元(含税,扣税后249.057元)
    2015-07-17           43.74 10送1.00派43.74元(含税,扣税后39.266元)
    2006-05-19             3.0 10转10.00派3.00元(含税,扣税后2.70元)

  ⇒ 换算：PRETAX_BONUS_RMB / 10 = 每股派息（元）。茅台最高精度为 5 位小数（28.02423），
    故库内必须存**微元/股**（分与厘都不够）—— 与 #8 的结论一致。

  另注：日期区间过滤会返回**北交所代码**（实测含 920663.BJ）。#7 R3 已把标的限定为
  `sh`/`sz` 六位码 ⇒ 与持仓求交时天然排除，但解析层不应假设返回的都是 `sh`/`sz`。
  且区间过滤会返回**尚未实施的未来除权日**（实测查到 2026-09-22）——
  本票已决定**不做提前告知**，故检测窗口取「目标交易日 == 除权日」当天即可。

[6] 浮点转「分」陷阱 —— 报价是元字符串，入库要整数分
==============================================================================

  报价字符串     float(x) * 100               int()   round() 判定
  152.710        15271.0                      15271     15271 一致
  152.290        15229.0                      15229     15229 一致
  1.150          114.99999999999999             114       115 **不同 ⇒ 截断即错**
  0.290          28.999999999999996              28        29 **不同 ⇒ 截断即错**
  1168.630       116863.00000000001          116863    116863 一致
  1212.100       121209.99999999999          121209    121210 **不同 ⇒ 截断即错**
  150.560        15056.0                      15056     15056 一致

  3 / 7 个样例上 int() 与 round() 不同 ⇒ **必须 round()，不得截断**。
  正确写法：`Math.round(parseFloat(s) * 100)`（JS）/ `int(round(float(s) * 100))`（Python）。

  编码与格式差异（实测）：
    源         编码       价格小数位   日期字段
    腾讯       GBK        2 位         f30 = YYYYMMDDHHMMSS（如 20260915161438）
    新浪       GBK        3 位         f30 = YYYY-MM-DD（如 2026-09-15）
    东财       UTF-8      2 位         f51 = YYYY-MM-DD
  A 股股票的最小价格变动单位是 0.01 元 ⇒ 新浪的第 3 位小数应恒为 0；
  若出现非 0（如 152.715），说明口径异常 ⇒ 记 warn，不要静默取整。

[7] 运行结果三态与连续失败计数 —— skipped 必须被「跳过」而不是「重置」
==============================================================================

  三态定义（本票 Q4）：
    ok      = 抓到目标交易日的行情并落库
    skipped = **至少一个源给出了明确响应的日期否定** ⇒ 非交易日（法定节假日/周末）
    failed  = 无响应 / 超时 / 解码失败 / 字段不足 / 最新价 <= 0 / 日期为旧且无源可确证

  最近若干次结果                        连续 failed 告警                   校验
  ok → failed → failed                            2 站内高优先级           ✓
  failed → skipped → failed                       2 站内高优先级           ✓
  ok → failed → skipped                           1 —                      ✓
  failed → ok → failed                            1 —                      ✓
  ok → ok → ok                                    0 —                      ✓
  skipped → skipped                               0 —                      ✓

  「skipped 跳过」的语义要点：failed → skipped → failed 记为**连续 2 次**。
  这是对的 —— 中间的 skipped 只说明那天休市，两次失败仍落在相邻的两个**交易日**上。
  若改成「skipped 重置」，节假日会把失败 streak 无声清零，漏掉真故障。

  落库与查询演示（3 个交易日窗口，第 2 天休市）：

    run_date      result    error
    2026-09-28    ok                                                                subreq=2 rows=31
    2026-09-29    failed    AbortError: timeout after 5000ms (tx)                   subreq=2 rows=0
    2026-09-30    skipped   所有源均返回 2026-09-29 的数据 ⇒ 非交易日               subreq=2 rows=0
    2026-10-08    failed    HTTP 502 (tx) / 解码失败 (sina)                         subreq=2 rows=0

    正确算法（跳过 skipped）                     连续 failed = 2     
    错误算法（把整个历史的 failed 都数一遍）     2                   
    两者在这里恰好都等于 2，但语义不同：
      前者问「最近是否连续失败」，后者问「历史上失败过几次」。
      一旦中间出现一次 ok，正确答案归零、错误答案不清零 —— 用一个反例坐实：
      真实序列（尾部）= failed → failed → ok → failed
      正确算法（最近连续 failed）                  1                   
      错误算法（failed 总数，跨全部历史）          5                   
      ⇒ 错误算法会持续报警到永远；正确算法在 2026-11-04 那天立刻归零。

[8] 一次运行的请求预算
==============================================================================

  平台事实：外部子请求上限 = 50 /invocation；D1 等内部服务 = 1000 /invocation。
  实测场景：持仓 50 只。

  场景                                   请求数    vs 上限 结论
  A 常态（行情 1 + 除权 1）                   2         4% 余量充足 ✓
  B 自愈日（+ 回填 ≤10 只 × 2）              22        44% 余量充足 ✓
  C 盲扫反事实（每天查全部持仓缺口）        102       204% **超上限 ✗**

  ⇒ 事件触发的自愈（本票 Q10）把常态压到 **2** 个请求；
    而按「每天为每只持仓股拉区间查缺口」实现，50 只就会打到 102 个请求，**直接击穿上限**。
  另注：同 host 同时「等响应头」的连接上限为 6 ⇒ 即使并发也要 ≤6，且本场景无需并发。
  D1 写入走内部服务预算（1000），与外部子请求的 50 是两套额度。

[9] 结论
==============================================================================
1. **昨收只有一条可靠通路：当日实时 feed 的昨收字段**，且主备源（腾讯/新浪）在除权日
   都等于交易所参考价（样本 A 两源同为 150.56 = 152.21 − 1.65）⇒ 主备切换不会造成假暴跌。
2. 本地未复权前收、kline 的 f60、单日窗口 preKPrice **三条通路全部不可用**；
   前复权序列只在「其后无送转 / 无除权」时可用，加差分修正后可在全域精确——
   但**必须配白名单校验**（非除权日算出的值须等于 fqt0(D−1)，否则置 NULL）。
3. fqt=1 序列对长历史会出**负值**（样本 B 2015 年 ≈ −70 元）⇒ 只能取差分，不能当价格。
4. 东财 kline 的 f60 在同一接口内对不同除权日采用不同基准（最近一次用参考价、更早用未调整前收），
   机制未查明 ⇒ 不得用于反推昨收。
5. 单日窗口 preKPrice 在非交易日返回 **0.0 且 klines 为空**；该 0.0 会穿过所有
   「非空/可解析」校验 ⇒ **prev_close <= 0 必须与「最新价 == 0」同样判为无效**。
6. 分红接口三种过滤形态均实测可用（单码/多码 in/日期区间）；**日期区间可让 N 只股票只用 1 个请求**。
   但返回中含 **ex_date 为 null 的预案**，实测：「过滤 null」与「唯一约束」**缺一不可**——
   光有 `(成员,代码,除权日)` 唯一键挡不住 null（唯一约束对 NULL 不生效，实测 2 次抓取各插一条），
   光过滤 null 而不加唯一键则所有记录都会增殖。
7. 报价字符串转「分」**必须 round() 不得截断**（7 个样例中 3 个 int() 与 round() 不同）；
   腾讯/新浪为 GBK、东财为 UTF-8；新浪价格 3 位小数。
8. 连续失败计数**必须跳过 skipped 而非重置**：failed → skipped → failed = 连续 2 次；
   用「failed 总数」代替「最近连续 failed」会报警到永远。
9. 事件触发的自愈把常态请求压到 **2/次**；按「每天盲扫全部持仓缺口」实现会击穿上限。
